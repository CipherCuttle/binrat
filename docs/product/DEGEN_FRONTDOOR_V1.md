# BINRAT DEGEN FRONTDOOR V1

**Status:** product presentation authority for the public frontdoor  
**Base:** `integration/binrat-case-canonical-v1@9e8b37ec0a643aadf8aaf789e9ab6c4ae4b85cb3`  
**Scope:** presentation / acquisition / narrative composition only

This document defines how BINRAT explains itself before a user enters the evidence-heavy product.

It does **not** change evidence truth, capability truth, token-launch authority, Watch semantics, Telegram authority, deployment state, financial claims, or product permissions.

The frontdoor has one job:

> **Make a new user understand why the Rat matters before showing them the machinery underneath.**

## 1. Product thesis

BINRAT is **dumpster intelligence for crypto launches**.

New launches hit the bin. The Rat remembers the scraps, follows recurring trails, preserves receipts, and can leave a tripwire on something worth watching.

The product should feel like:

> **memecoin gossip with evidence underneath**

not:

- a generic analytics dashboard with rat branding;
- a trading terminal;
- a risk-score product;
- an alpha feed;
- a compliance memo;
- a token landing page with a scanner attached.

The durable tension is:

> **FERAL PRESENTATION. BORING TRUTH.**

And the permanent rule remains:

> **DEGEN DECIDES ATTENTION. RECEIPTS DECIDE TRUTH.**

## 3. Frontdoor success condition

A first-time visitor should be able to answer within roughly 10–20 seconds:

1. **What did the Rat find?**
2. **Why does it smell interesting?**
3. **What can I do next?**
4. **Why does Telegram matter?**
5. **Where is BINRAT going?**
6. **What is $BINRAT for?**

If the user leaves with only:

> “It is a blockchain analytics dashboard.”

the frontdoor failed.

If the user leaves with:

> “It is a memecoin trading bot.”

the frontdoor also failed.

The intended understanding is closer to:

> **A feral launch-intelligence rat that remembers old trails, shows the receipts, and squeaks when watched things come back.**

## 4. Canonical frontdoor journey

The public acquisition path is:

```
LAND
 ↓
FOUND SOMETHING
 ↓
WHY CARE?
 ↓
FRESH GARBAGE
 ↓
DIG DEEPER
 ↓
RAT TRAP / TRASH TRAIL
 ↓
WATCH IT
 ↓
TELEGRAM SQUEAKS LATER
```

The frontdoor should sell **why**.

The app should prove it with **evidence**.

### Stage A — LAND

First viewport must communicate:
- Rat identity;
- launch-intelligence job;
- memory/recurrence advantage;
- two obvious actions.

Target hierarchy:

> **THE RAT FOUND SOMETHING.**

Literal explanation:

> New launches hit the dumpster every day. BINRAT remembers the trails they leave behind and can squeak when familiar paws come back.

Primary CTA:

> **OPEN FRESH GARBAGE →**

Secondary CTA:

> **GET THE TELEGRAM RAT →**

Trust line:

> **DON'T TRUST THE RAT. CHECK THE RECEIPT.**

The first viewport should not lead with:
- block/checkpoint numbers;
- coverage machinery;
- large evidence tables;
- raw database terminology;
- token legal state;
- internal runtime state.

Those remain available deeper.

### Stage B — FOUND SOMETHING / FRESH GARBAGE

Use one current finding to demonstrate the product.

Shape:

```
FRESH GARBAGE
$TOKEN

SMELLS FAMILIAR.
Same source-reported deployer appears on 4 retained launches.

DIG DEEPER →
```

Rules:
- lead with the current launch/token;
- explain the shortest factual reason it surfaced;
- show recognizable prior scraps where available;
- do not turn recurrence into skill, intent, identity, safety or profitability;
- do not ask for Watch before showing why the trail matters.

### Stage C — DIG DEEPER

Turn the finding into a compact story.

User questions:

- What launched?
- Why did BINRAT notice it?
- What earlier projects connect to this trail?
- What historical facts are actually supported?
- What is still missing?

This layer should progressively disclose evidence rather than dump raw provenance immediately.

Raw receipts stay available as the trust escape hatch.

### Stage D — RAT TRAP / TRASH TRAIL

Answer:

> **What happened the other times these paws showed up?**

Only supported historical context may appear.

No prediction is authorized.

Missing / partial outcome coverage stays explicit.

### Stage E — RAT WATCH

After the trail is meaningful:

> **Leave a tripwire in the trash.**

Supported promise:

> **I'll squeak if these paws launch again.**

Watch is monitoring, not a trading recommendation.

### Stage F — TELEGRAM

Telegram is the retention surface.

The frontdoor should explain it as:

> **THE RAT LIVES IN TELEGRAM.**

Supporting idea:

> You should not have to stare at the terminal waiting for trash to move. Find a trail, leave a tripwire, and let the Rat squeak when the configured event happens.

Canonical surface split:

- Telegram: scout / discovery / DIG / Watch / alerts / bounded WHY / share;
- Web: deeper Case / history / Replay / receipts / relationships;
- shared backend: one evidence and Watch authority.

The website should visibly expose the Telegram entry point.

## 6. $BINRAT narrative

The frontdoor should explain purpose before legal/status detail.

Target entry concept:

> **THE RAT NEEDS A COIN.**

Literal explanation:

> **$BINRAT is the culture and coordination layer around BINRAT. The product stays useful without it. The coin can progressively support access, coordination, hunts, bounties and later evidence-network mechanics as those capabilities actually ship.**

Core doctrine:
- fair-launch intent;
- no private presale;
- no hidden team allocation;
- disclosed project/creator fee routes;
- disclosed treasury/funding surfaces;
- core receipts remain public;
- token ownership never decides factual truth;
- no promise of returns or appreciation.

### Utility horizons

#### Launch / early
Candidate utility may include:
- deeper Rat Radar access;
- more Rat Watch capacity;
- richer filters;
- Rat Den access;
- visible treasury/fee transparency.

#### Growing utility
Candidate utility may include:
- Trash Hunts;
- Bounty Boost;
- Case Sponsor;
- Dumpster Raid priority signaling;
- Rat Credits / Rat Reputation coordination.

#### Network utility
Later, separately authorized mechanics may include:
- bonded submissions;
- bonded challenges;
- anti-spam / Sybil cost;
- Rat Node bonds.

Every user-facing utility item must show its actual canonical state, such as:
- `PUBLIC_LIVE`;
- `BUILDING`;
- `PLANNED`;
- `EXPERIMENTAL`.

The frontdoor must never imply planned token utility is live.

Current anti-scam state remains prominent where relevant:
- no official contract unless canonical launch state says otherwise;
- no unofficial address may be presented as official;
- no launch authority is created by this document.

## 11. Falsification / kill criteria

Frontdoor V1 fails if any of these are true:

1. A cold user still describes BINRAT only as “a blockchain analytics dashboard.”
2. The page implies BINRAT is a trading bot.
3. Telegram is still effectively invisible.
4. The roadmap exists but does not help the user imagine the product's progression.
5. $BINRAT is either hidden or presented primarily as speculative upside.
6. Planned capability is presented as live.
7. Evidence language becomes less precise in exchange for degen tone.
8. The implementation requires rewriting the intelligence backend.
9. Visual work drifts from Rat Zero / Brand V1 / raster authority.
10. The first useful action is buried behind forensic detail.

## 13. Cold-user comprehension gate

Before this frontdoor is considered done, a cold user must be able to recover the product model without reading internal documentation.

### 5-second test

The user should understand:

> **BINRAT remembers old launch trails so a new launch does not start from zero.**

They should see two obvious next actions:

- open Fresh Garbage;
- get the Telegram Rat.

### 10-second test

The user should be able to explain, in their own words:

> **BINRAT watches fresh launches, remembers earlier launches tied to the same Pons-reported deployer, and shows the receipts.**

Failure states:

- “It is just a crypto dashboard.”
- “It tells me what to buy.”
- “I have no idea why the old launches matter.”

### 30-second test

The user should understand:

- Web BINRAT = investigate the trail and receipts;
- Telegram = tell me when a watched trail moves again;
- roadmap = where the Rat is going, not a promise calendar;
- $BINRAT = product/culture/coordination layer, not evidence authority.

The information hierarchy must be:

```
HERO
↓
ONE REAL / CURRENT PROOF STORY
↓
FRESH GARBAGE / PRODUCT
↓
TELEGRAM RETENTION LOOP
↓
ROADMAP
↓
METHOD / RECEIPTS / TOKEN DETAIL
```

Do not put roadmap fantasy ahead of demonstrating current product value.
