## Owner constraint and decisive tradeoff

No recruited human testers or manual beta-user dependency. Build for an owner-selected **capacity target** of 10,000 daily active users, 1,000 simultaneously open client sessions, 100 mixed API requests/second sustained for 30 minutes, and 300 requests/second burst for 5 minutes. These values are test targets, not measured capability, demand forecasts or a promise of a launch-day customer count. 1,000 open client sessions do not imply 1,000 requests/second; model realistic polling and cold-cache behavior separately.

No tester dependency means we can verify engineering capacity, source fidelity, economics stress and synthetic UX flows **but cannot prove product-market fit, discover all comprehension failures, or show real paid conversion** before actual user traffic. Do not mislabel a load-test pass as real demand. Real automated production telemetry must replace beta feedback after permitted public launch.

**Economics nonnegotiable:** token trading fees = ZERO in solvency gate. A full two-chain public product must be cost-capped, not free unlimited computational service. Token launch/legal/security/custody approvals remain separate from this architecture readiness plan.

## V0 deployment layout — minimal isolation, not premature microservices

Shared public frontend/API remains a Cloudflare Worker with static assets and caching. **Never fetch chain RPC inside a public request to build the common feed.** Publish immutable/canonical evidence references and versioned cached per-chain projection snapshots for public reads. Cache by chain, projection version, canonical block hash or generation and explicit freshness contract. Ensure API 503/STALE response is truthful under lag; stale content must identify its last verified source point. Cache never becomes receipt authority.

Separate independent Arc and Robinhood ingestion workers / Queue consumer groups with per-chain bounded RPC windows, finality/reorg policy, checkpoints, retry DLQs and prioritized live-over-backfill lanes. Arc existing authoritative receipt history remains immutable. 4663 needs genuinely verified current Pons V2 factory/emitter, curve and separate graduation/V4 schemas from real on-chain evidence; contract-read launch preflight is not an indexer. New Robinhood writes MUST NOT share Arc lease or claim source equivalence.

For D1 start by preserving the working existing Arc evidence database and use **a distinct 4663 evidence database when engineering the new source**, rather than funnel both high-write chains into one hot database. A separate small account/entitlement database is warranted before live subscriptions to isolate payment-control writes from chain backfills. D1 databases are single-threaded per database and constrained to 10GB each on Workers Paid. Avoid immediate per-user or per-pool sharding; split/hotspot only if indexed query/size/latency evidence demonstrates need. No migrations to existing Arc D1 without a versioned read-compatible rehearsal and authorized production rollout.

Telegram webhook should authenticate, durably deduplicate and acknowledge quickly; costly conversation/research or mass-alert work must be bounded and queued rather than letting a single webhook force synchronous expensive RPC/DB work on the shared public API Worker. One independently budgeted alerts Queue (if existing live Watch delivery is staged separately) produces deterministic **event × eligible subscription** IDs with chainId in every key, a persisted outbox or equivalent reservation, idempotent retry, exponential delay on HTTP 429, and dead-letter queue after bounded retry. Avoid recomputing chain evidence once for each subscriber. Target standard Telegram global broadcast <=25 successful sends/second, and <=1 message/second/chat, with a token-bucket reservation for higher paid delivery priority only when capacity exists. A 10K-recipient global event requires many minutes of delivery under free Telegram limits; never promise instantaneous delivery to all. Suppress duplicate material and offer digest options.

One account + entitlements service (can remain Worker module, not a new dedicated server) validates signed, idempotent provider events, refund/reversal, server-side prepaid metered quotas and optional chain-4663 holder eligibility AFTER the actual token/legal gate. Never write a D1 row for every public GET or query wallet balance on every request. For expensive authenticated operations, allocate atomic consumption credits using a tested per-account budget mechanism (transactional D1 if actual serialization is sufficient, or Durable Object per usage key if atomic high-contention tests require it); reconcile grants, invoices and consumption in the account store. Same account quota spans Arc and Robinhood if the purchased product says so.

Static site & read-only public receipts degrade gracefully when Telegram, holder RPC, payment processor or a source RPC fails. Fail closed for paid *extras* and high-cost operations on authority failure; do not fail open to unlimited capacity.

## Metering and cost controls that work without recruited testers

Instrument per route/cache status/chain and source job: Worker invocation and CPU, D1 rows read/written/query time and GB, Queue send/read/retry/DLQ counts, RPC calls and upstream provider billing, Telegram delivered/429/error, live index lag, per-tier work units, monthly collected net-of-refund+VAT revenues. Publish an internal founder-only dashboard showing TODAY SPEND, MONTH FORECAST, maximum free-user subsidy, available cash runway and ability to disable only costly optional operations.

Set **user-level / account-level / chain-level / global** resource gates. No hard limit is claimed unless implemented at the origin/work queue: Cloudflare billing notifications by themselves are NOT cost ceilings. Application-level quotas can hard-stop self-initiated RPC, costly database jobs, paid work and Telegram fanout, but cannot by themselves guarantee a hard dollar ceiling on hostile inbound Worker requests already admitted by Cloudflare. Use upstream WAF/challenge rules where authorized, per-route rejection before expensive work, budget alarms, emergency route disable and a founder-authorized residual maximum exposure. Distinguish an alert threshold from a billing cap. Tiered degrade ladder:
1. reduce backfill and expensive historical recomputations; maintain live verified intake + immutable receipts;
2. serve versioned public cached snapshots longer with **explicit freshness timestamp** and mark source status STALE/PARTIAL;
3. shed optional free high-frequency alerts and exports while preserving basic receipts and paid committed quotas up to prepaid capacity; honestly disclose delayed notifications;
4. stop accepting *new* expensive promises/subscriptions if prepaid reserve cannot cover commitments; do not silently revoke already purchased access without terms and remediation;
5. protect payment/account endpoints and canonical source integrity first. Never falsely output NO_RISK/NO_LAUNCH on upstream failure.

Workers Paid is a REQUIREMENT before the proposed full 100-RPS × 30-minute isolated load benchmark if every tested request invokes a Worker: that single run alone generates 180,000 Worker requests, exceeding Workers Free's 100,000/day limit. Do not point the full benchmark at a production Free account. Current official documentation says Free has 100,000 Worker requests/day, D1 Free 100,000 written rows/day and 500MB maximum single DB; D1 Paid 10GB max each and usage billing. Paid Workers minimum $5/month, D1 Paid includes 25B read rows, 50M written rows and 5GB storage monthly before marginal fees (CHECK fresh official docs and real account contract at action time). Low unit prices do NOT prove project margin: paid RPC/archive, Telegram amplification, incident support, founder time and legal/audit costs may dominate.

**Illustrative conversion risk**: 10K daily users with 1% paying produces 100 seats; if an assumed $29 consumer price includes 25% VAT, 8% payment/refund haircut and $4 variable paid-seat cost, modeled contribution per seat is $16.88; $1,688 monthly paid contribution still fails an invented $2,000 fixed-cost scenario. At 2% paying the same assumptions produce $3,376 before fixed cost. This is arithmetic on synthetic inputs, NOT expected conversion or a VAT determination. ZERO conversion must be an explicit 10K DAU cost stress, not an edge case omitted from launch budget. Prepaid Pro and optional **separately funded** holder bonuses have hard unit ceilings. Project creator fees are not in the survival model.
