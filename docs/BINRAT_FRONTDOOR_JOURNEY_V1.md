# BINRAT — FRONTDOOR JOURNEY V1

Date: 2026-10-05  
Project: CipherCuttle/binrat  
Status: FROZEN DESIGN CONTRACT within this session. Not implemented, deployed, or independently usability-tested.  
Authority: Owner-supplied Rat Workforce + Frontdoor handoff. Current repository/runtime state has not been reverified here.

## PLAN

Freeze one understandable journey: FIND → EMPLOY → LEAVE → RETURN.

The first click must deliver discovery. Crew teaches which worker owns which job. A Case supplies evidence and contextual employment. Den supplies job control. Telegram brings the user back.

Preserve the approved Rat Zero, Tripwire and Sniffer identities and Rat Select donor material. No new artwork, frontend code, repository changes or public publication are part of this document.

A critical constraint: the product vision contains persistent jobs that the frozen roster still marks BUILDING and NEXT. The design must teach the complete loop without presenting those jobs as available today.

## CHANGESET — 1. The ten-second message

Exact hero:

**YOU CAN'T WATCH ALL THIS SHIT.**  
**YOUR RATS CAN.**

Literal explanation:

**Rat Zero checks fresh Pons launches and shows what BINRAT remembers. Persistent watchers and funding hunters are coming next.**

Primary CTA: **START DIGGING**  
Secondary CTA: **MEET THE CREW**

Availability strip:

**RAT ZERO · LIVE / TRIPWIRE · BUILDING / SNIFFER · NEXT**

Compact loop:

**FIND → EMPLOY → LEAVE → RETURN**

Supporting line:

**Find something. Leave a Rat on it. Go away.**

Keep the availability strip beside the explanation; do not bury it below the fold. The supporting line describes the workforce direction. The visible statuses constrain what users can actually do now.

START DIGGING opens fresh Pons discovery. It does not open Rat Select, require a wallet, create a job, charge money or imply trade execution.

Acceptance target, not a proven result: after ten seconds, a newcomer should say “It helps me investigate crypto launches; eventually I can leave workers watching them; Rat Zero is the one I can use now.”

## CHANGESET — 3. Exact homepage order

### 1. Hero

Use the copy above. Preserve the approved visual identity. A missing hero raster cannot block freezing or testing the journey; the first viewport must explain the product even with imagery absent.

### 2. Fresh proof

Headline: **WHAT JUST HIT THE DUMPSTER?**

Literal explanation: **Fresh Pons launches. Open one to see what the Rat found.**

Show up to three real, supported launch cards, newest first for this slice. No new “trending” algorithm is required.

Each card contains:

- Token name/ticker, with a readable address fallback.
- Robinhood / Pons context.
- Launch time, distinct from BINRAT’s last verification time.
- One supported reason to open the Case, when available.

Example copy pattern only: “This deployer launched before.” The actual statement requires a receipt. If the history is unknown, say “Creator history not checked” or omit the reason. Do not manufacture a curiosity hook.

Section CTA: **OPEN THE DUMPSTER**.

Do not add risk scores, winner predictions, invented live counts or a meaningless RATS total.

## CHANGESET — 4. Dumpster → Case → job

Dumpster is discovery, not a second marketing page. Preserve feed/filter WIP and the existing evidence contract.

Case begins with:

1. Subject: token/address, chain and source context.
2. **WHAT THE RAT FOUND**: a short supported summary.
3. Verification/coverage context in plain language.
4. Relevant action.
5. Expandable evidence and receipts.

A technical detail matters if it changes how the user should interpret the finding. Otherwise keep it deeper in the Case.

Contextual actions:

| Case context | Future employment CTA | Current behavior |
| --- | --- | --- |
| Supported funding trail | SEND SNIFFER DOWN THIS TRAIL | Show SNIFFER · NEXT detail; create no job |
| Creator worth monitoring | LEAVE TRIPWIRE HERE | Show TRIPWIRE · BUILDING detail; create no job |
| Fresh Pons launch | Rat Zero’s supported Case digging | Use the existing LIVE path after verifying its behavior |
| Missing funding evidence | No Sniffer employment action | Explain what evidence is missing |
| Stale/partial coverage | Coverage explanation | Do not present absence as a clean result |

Unavailable controls use explicit labels such as **SNIFFER · NEXT — SEE THE JOB**, not an apparently active employment button that fails after clicking.

The action contract is fixed now. Activation is a separate acceptance decision.

## CHANGESET — 5. Future employment confirmation

One user request creates one user-facing job, even when specialists exchange typed work.

Before a persistent job starts, show:

- What the Rat will follow.
- What qualifies as a finding.
- When it will stop.
- Its work/cost limit.
- Where the user will receive updates.
- Whether capacity is reserved or additional payment is required.

Example structure, not frozen economics:

**LEAVE TRIPWIRE HERE**  
Watch this deployer for another Pons launch.  
Stops on the displayed date or if its work limit is exhausted.  
Delivery: the user’s connected Telegram account.  
[ START JOB ]

Do not ask users to configure agent frameworks or handoff graphs. Do not imply that a workforce job can trade.

A job exists only after durable admission succeeds. A rejected or uncertain request must not appear as a working Rat.

At a real capacity wall:

**ALL YOUR RATS ARE WORKING.**

Offer review/stop of existing jobs first. Temporary paid capacity and active-stake capacity can appear only after those mechanisms are implemented, cost-bounded and authorized. Counts come from actual admitted jobs and capacity, never canned “2 / 2” copy.

## CHANGESET — 6. Den

Headline: **THE DEN**.

When implemented, show the real number of occupied slots and one row per user-facing job. A specialist handoff remains inside its originating job; it does not generate a surprise swarm or hidden capacity charge.

Each row shows:

- Lead Rat and subject.
- Plain-language assignment.
- Current state and last meaningful activity.
- End date and available work limit.
- Delivery connection.
- OPEN JOB; OPEN CASE when relevant; STOP JOB when running.

| State | Meaning to the user |
| --- | --- |
| SLEEPING | Watching; no qualifying change yet. |
| WORKING | Processing a qualifying event or requested dig. |
| WAITING | Blocked on a named dependency or required user action. |
| FOUND | There is an unseen supported finding to inspect. |
| DEGRADED | Coverage or delivery is impaired; show the specific limitation. |
| DONE | Finished or stopped; explain why. |

SNIFFING can be personality text. The control plane still uses the consistent state vocabulary.

A sleeping Rat is successful when nothing warrants an interruption. Do not animate busyness or show fake reasoning streams to justify the subscription.

FOUND is also an unread-finding indicator. After reading, the job may return to SLEEPING if it is still watching. A terminal or degraded job can retain an unread finding. Do not erase the finding merely because the lifecycle state changes.

Empty live Den:

**NO RATS OUT YET.**  
**Find something worth watching.**

CTA: **OPEN THE DUMPSTER**.

Until persistent jobs are supported, use the clearly marked Crew explanation instead of this live empty state.

## CHANGESET — 7. Telegram → return

Future alert:

**🐀 FOUND SOMETHING.**

Then:

- The watched subject.
- What changed.
- Why this matches the job’s condition.
- The limitation, if material.
- **OPEN UPDATED CASE**.

The destination opens the relevant Case with its diff in focus, not Home, Crew or an unrelated feed.

Return view:

**WHAT CHANGED WHILE YOU WERE GONE**

Distinguish the new evidence from what was known before. Preserve chronology: evidenced funding first, later launch second. Do not convert funding into a “same team” identity claim.

“No useful change” produces no wakeup. Delivery failure appears in Den; it must not silently look like successful watching with a working return channel.

The same job can be inspected from Den without Telegram. Delivery is a return mechanism, not the sole record of the investigation.

## CHANGESET — 8. Visual and mobile contract

- Preserve approved raster Rat identities. No regeneration, mirroring or substitute mascot.
- Use Geist Sans for explanation and actions; Geist Mono for concise identifiers and status.
- Body explanation target: at least 16 CSS px. Important status/labels: at least 14 CSS px. These are chosen design targets, not evidence of accessibility compliance.
- Give primary touch controls at least a 44 × 44 CSS px target.
- At 390 × 844, the hero must expose the headline, literal explanation, availability and primary CTA without a horizontal scroll.
- Crew cards stack on mobile. The complete roster belongs on Crew; do not force visitors to swipe through five Rats to discover the product.
- Case receipts may expand; main explanations may not require expansion to understand the finding.
- Status must use text, not color alone.
- Add visible focus states and preserve reading order; validate contrast and zoom during implementation.
- Keep motion restrained and optional. No endless glitch layer competing with text.
- Reuse desktop and mobile Rat Select donor assets/components where they serve these rules. Do not infer current asset filenames or provenance from this document.

## CHANGESET — 9. Failure behavior

| Failure | Required behavior |
| --- | --- |
| Feed initially loading | Explain that Pons launches are loading; preserve layout |
| No verified snapshot | “Launches unavailable right now.” Provide retry; do not invent cards |
| Previously verified feed becomes stale | Retain it with verification age and stale context; do not label it fresh |
| Healthy empty feed | “No launches in this view.” Distinguish from unavailable data |
| Unsupported subject | Explain coverage; do not create a useless job |
| Job admission rejected | Explain the limit; no working row or charge |
| Submission outcome uncertain | Reconcile the original request; do not invite duplicate job creation |
| Budget exhausted | Stop expensive work; record the reason and show renewal options only when real |
| Telegram disconnected | Explain delivery impairment; preserve the job and findings |
| Rat not yet available | Show its status/detail; create no job |

Do not reinterpret a healthy website as proof of healthy index coverage or successful alert delivery.

## VERIFY — bounded design review

This is a self-review of the design contract, not a repository audit or an independent hostile implementation review.

| Challenge | Resolution in this contract |
| --- | --- |
| Hero promises workers before persistent jobs exist | Adjacent availability strip and literal current-state explanation |
| Rat Select hijacks the first action | START DIGGING goes directly to discovery |
| Roadmap imitates working product | BUILDING/NEXT controls open explanations; examples are visibly labeled |
| Token CTA exceeds publication authority | Token language remains internal until its gate permits publication |
| Telegram click implies enrollment | Bot opening and verified job-delivery connection are separate |
| Den has fake motion/counts | Only admitted jobs and real events supply state |
| Paid investigation buys different truth | Shared Case evidence rules remain invariant |
| A handoff becomes multiple unexpected jobs | One origin job contains bounded specialist activity |
| Feed outage looks like no launches | Healthy empty, stale and unavailable states differ |
| Reading FOUND accidentally ends watching | Lifecycle and unread finding are tracked separately |

No Critical/High design conflict remains identified in this review. Capability availability remains unverified. The main assumption to test is whether newcomers understand the workforce loop while recognizing that only Rat Zero is live.

Smallest comprehension experiment:

Show the first viewport and one real Case to five people unfamiliar with BINRAT for ten seconds. Hide the screen. Ask:

1. What does this help you do?
2. What happens when you press START DIGGING?
3. Which Rat can you use today?
4. What would bring you back after leaving a future job?

Target: at least four of five understand the current action and availability. Treat this as a qualitative usability gate, not a statistical claim. If they think it is a trading bot, believe Sniffer is already available, or cannot identify the first click, revise the copy before pixel-polishing.

## VERDICT — smallest implementation sequence

**BUILD THE FRONTDOOR JOURNEY AS A BOUNDED SLICE. PROVE THE WORKFORCE SEPARATELY.**

No frontend code has been written in this session.

1. **Inventory before editing.** Pin the current candidate base, WIP, approved asset provenance, real routes, Rat Zero behavior and bot destination. Preserve existing work. Do not mix branches casually.
2. **Frontdoor only.** Compose Home, navigation and Crew from donors. Reuse existing read surfaces. Keep BUILDING/NEXT actions explanatory. Keep public token promotion gated. No runtime autonomy or economics changes.
3. **Verify the current user path.** Home → Dumpster → Case; Home → Crew; correct Telegram destination; mobile readability; loading/stale/unavailable behavior. Then one hostile review, fix Critical/High, one targeted rereview, stop.
4. **Offline workforce contracts.** Define the seven named V1 schemas, three profiles and one executable Sniffer fixture. Validate outside-model policy, budget and typed handoff invariants.
5. **One offline/shadow end-to-end proof.** Evidenced funding → qualifying recipient → later Pons deployer → Rat Zero handoff → Case diff → alert artifact. Record no-match, partial coverage and duplicate/restart behavior. No production autonomy or unsolicited Telegram sending.
6. **Measure before pricing.** Bound worst-case job spend, waiting costs, handoffs, retries and provider exposure. Only then propose fiat/stake capacity economics; do not freeze them here.
7. **Expose real jobs.** Den and a simple structured employment flow first. Add chat over the same job contracts after admission and lifecycle behavior work. Activate persistent employment only with explicit owner authorization.

Acceptance gates matter more than PR count. Keep these slices isolated enough to roll back the presentation without changing evidence, existing watches or runtime state.

Still not authorized: merge, deploy, public token marketing, token launch, signing/broadcast, autonomous trading, capital authority, unlimited AI, final pricing/stake amounts or bypassing legal/Pons/staking gates.

Frozen design verdict:

**Home sells the loop. Dumpster delivers the first proof. Case earns trust. Crew explains the workers. Den controls real work. Telegram brings the user back. $BINRAT reserves bounded labor when authorized.**
